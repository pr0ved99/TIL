# 공터에서 쓰레기를 줍는 자율주행 로봇 개발 단계별 로드맵

## 0. 결론

- 지금 너희 프로젝트는 `VSLAM 단독 기반 로봇`이 아니라 `GPS + 엔코더 + IMU + D435i + Nav2 + 쓰레기 탐지 + 수거 장치`를 합친 실외 자율주행 시스템으로 보는 것이 맞다.
- 공터처럼 특징점이 부족한 환경에서는 `카메라 기반 VSLAM`을 주 위치추정 수단으로 두기보다, `GPS 기반 전역 위치 + 엔코더/IMU 기반 로컬 오도메트리` 구조로 가는 것이 훨씬 현실적이다.
- D435i는 전역 위치추정보다 `근거리 장애물 확인`, `쓰레기 탐지`, `마지막 정밀 접근`에 쓰는 것이 더 적합하다.

## 1. 먼저 큰 그림을 이해하기

직관:
자율주행이 완성된다는 것은 "로봇이 스스로 돌아다닌다"가 끝이 아니다. 자기 위치를 알고, 목적지를 향해 이동하고, 쓰레기를 발견하고, 가까이 가서, 집고, 다시 이동할 수 있어야 한다.

핵심 개념:
- `Localization(위치추정)`: 로봇이 현재 어디 있는지 아는 것
- `Navigation(내비게이션)`: 목적지까지 경로를 짜고 실제로 가는 것
- `Perception(인지)`: 카메라로 쓰레기나 장애물을 인식하는 것
- `Manipulation(조작)`: 집게나 흡입기로 물체를 집는 것
- `Mission Control(임무 제어)`: 탐색, 접근, 수거, 복귀 순서를 관리하는 것

즉, 최종 시스템은 아래처럼 나뉜다.

```text
위치추정 + 주행 + 인지 + 집기 + 임무제어
```

## 2. 지금 가진 장비 기준 현실적인 해석

현재 확보한 장비:

- `D435i`
- `엔코더 달린 모터`
- `GPS`

의미:
- `D435i`: RGB 영상, depth, IMU를 제공
- `엔코더 모터`: 바퀴 회전량으로 오도메트리 계산 가능
- `GPS`: 실외 공터에서 전역 위치 추정 가능

중요한 판단:
- 공터는 특징점이 부족할 가능성이 높다.
- 따라서 `특징점 기반 VSLAM으로 방향/위치를 주력 보정`하는 설계는 불안정할 수 있다.
- 이 조건에서는 `GPS + 엔코더 + IMU`가 중심이고, `D435i`는 보조 센서로 쓰는 것이 맞다.

## 3. 추천 전체 아키텍처

가장 실용적인 추천 구조는 아래와 같다.

```text
GPS --------------------------> 전역 위치
엔코더 + IMU -----------------> 로컬 오도메트리(EKF)
D435i ------------------------> 근거리 인지 / 쓰레기 탐지 / 마지막 접근
전역 위치 + 로컬 위치 ---------> Nav2
카메라 탐지 결과 -------------> 접근 목표 생성
수거 장치 제어 ---------------> 집기 동작
상태기계 ---------------------> 전체 미션 제어
```

좌표계 역할도 분리하는 것이 좋다.

- `map`: 전역 기준 좌표계
- `odom`: 부드러운 로컬 기준 좌표계
- `base_link`: 로봇 본체 기준 좌표계

권장 역할:
- `GPS 포함 위치추정`: `map` 기준 위치 보정
- `엔코더 + IMU + EKF`: `odom -> base_link`
- `D435i`: 장애물/쓰레기/정밀 접근용

## 4. 왜 VSLAM을 주력으로 두지 않는가

직관:
VSLAM은 특징점이 잘 보이는 환경에서 강하다. 하지만 공터, 흙바닥, 잔디, 단조로운 야외 환경은 반복 추적할 특징이 부족할 수 있다.

핵심 개념:
- `Feature(특징점)`: 영상에서 다시 찾기 쉬운 점
- `Scale Drift`: 시간이 지나며 거리 비율이 틀어지는 현상
- `Outlier`: 잘못 매칭된 관측값

공터 환경의 문제:
- 바닥 패턴이 단조로움
- 조명 변화가 큼
- 햇빛 때문에 depth 품질 저하 가능
- 멀리 있는 물체가 많고 가까운 특징이 적음

결론:
- `VSLAM`: 선택적 보조
- `GPS + 엔코더 + IMU`: 주 위치추정

## 5. 개발 단계 전체 개요

자율주행 완료까지는 아래 순서로 가는 것이 좋다.

1. 로봇을 실제로 움직이게 만든다.
2. ROS2에서 센서 데이터를 안정적으로 읽는다.
3. 좌표계와 TF를 정리한다.
4. 엔코더 기반 오도메트리를 만든다.
5. IMU와 합쳐 로컬 위치추정을 안정화한다.
6. GPS를 붙여 전역 위치추정을 만든다.
7. Nav2로 목표점 이동을 성공시킨다.
8. D435i로 쓰레기 탐지를 붙인다.
9. 쓰레기 위치를 로봇 좌표계로 변환한다.
10. 마지막 접근 행동을 만든다.
11. 수거 장치를 제어한다.
12. 전체 미션 상태기계를 통합한다.
13. 실패 복구와 성능 평가를 추가한다.

## 6. 단계별 상세 진행방안

### Step 1. 로봇 베이스 조립과 수동 주행

직관:
자율주행 이전에 로봇이 기본적으로 똑바로 움직여야 한다.

구현:
- 차체 조립
- 모터 드라이버 연결
- 배터리/전원 연결
- 수동 속도 명령으로 전진/후진/회전 테스트

완료 기준:
- `cmd_vel` 입력으로 전진/후진/회전 가능
- 좌우 쏠림이 과도하지 않음

### Step 2. 센서 bring-up

구현:
- D435i 토픽 확인
- GPS 토픽 확인
- 엔코더 값 확인
- IMU 토픽 확인

우선 확인:
- `timestamp`
- `frame_id`
- 토픽 주기
- 데이터 끊김 여부

완료 기준:
- 모든 센서 토픽이 안정적으로 출력
- rosbag 기록 가능

### Step 3. 좌표계(TF) 정리

필수 좌표계 예시:

```text
map -> odom -> base_link -> camera_link
                         -> imu_link
                         -> gps_link
                         -> gripper_link
```

먼저 확인할 것:
- 카메라 방향
- IMU 축 방향
- GPS 안테나 위치
- 집게 기준점

흔한 실수:
- optical frame 축 반대로 이해
- IMU 축 반전
- 센서 위치를 대충 잡아서 접근 오차 발생

완료 기준:
- RViz2에서 TF 구조가 논리적으로 맞음

### Step 4. 엔코더 기반 오도메트리

직관:
바퀴 회전량은 짧은 구간 움직임을 부드럽게 추적하는 데 좋다.

구현:
- 엔코더로 이동 거리 계산
- `/odom` 발행
- `odom -> base_link` TF 발행

필수 점검:
- 바퀴 반지름
- 바퀴 간 거리
- 엔코더 방향 부호

완료 기준:
- 짧은 직진/회전에서 궤적이 크게 틀리지 않음

### Step 5. IMU 융합

직관:
엔코더만 쓰면 바닥 미끄러짐에 약하다. IMU를 같이 쓰면 회전 추정이 더 안정적이다.

핵심 개념:
- `EKF`: 여러 센서를 섞어 더 안정적인 자세를 만드는 필터

구현:
- `robot_localization`으로 encoder + IMU 융합
- `/odometry/filtered` 생성

완료 기준:
- 정지 상태 흔들림 감소
- 회전 시 yaw가 더 자연스러움

### Step 6. GPS 기반 전역 위치추정

직관:
공터에서는 이 단계가 핵심이다.

구현:
- GPS 드라이버 연결
- `NavSatFix` 토픽 확인
- `navsat_transform_node` 적용
- 전역 위치를 EKF에 반영

중요:
- GPS 위치는 튈 수 있다.
- 따라서 `GPS를 곧바로 로컬 제어용 odom`처럼 쓰지 말고, 전역 보정용으로 다루는 것이 좋다.

완료 기준:
- 공터에서 로봇 위치를 전역 기준으로 추적 가능

### Step 7. Nav2로 자동 이동

직관:
이제 "어디 있는지"를 아니까 "어디로 갈지"를 계산할 수 있다.

구현:
- Nav2 설정
- global/local costmap 설정
- waypoint 기반 이동

완료 기준:
- 지정한 좌표까지 자동 이동
- 기본 장애물 회피 수행

### Step 8. D435i로 근거리 인지

직관:
D435i는 공터 전체 위치추정보다 가까운 거리에서 더 유용하다.

구현:
- 근거리 장애물 확인
- 쓰레기 후보 탐지용 RGB 입력
- depth 기반 거리 계산

완료 기준:
- 카메라 앞 물체 거리와 방향을 추정 가능

### Step 9. 쓰레기 탐지

직관:
로봇이 이동만 잘해도 목적은 달성되지 않는다. 쓰레기를 찾아야 한다.

구현:
- 규칙 기반 또는 YOLO 기반 탐지
- bounding box 출력
- 탐지 confidence 기록

완료 기준:
- 쓰레기 후보를 안정적으로 인식

### Step 10. 쓰레기 3D 위치 계산

직관:
화면에서 찾았다는 것과 실제로 갈 수 있다는 것은 다르다.

구현:
- bounding box 중심 또는 mask 사용
- depth와 결합해서 3D 위치 추정
- `camera_link -> base_link` 변환

완료 기준:
- 쓰레기의 로봇 기준 위치 `(x, y, z)` 계산 가능

### Step 11. 마지막 접근 행동

직관:
GPS는 근처까지 가는 데 좋고, 마지막 정렬은 카메라가 더 잘한다.

구현:
- 쓰레기 앞 정지점 생성
- 저속 접근
- yaw 정렬
- 최종 정밀 정렬

완료 기준:
- 쓰레기 앞에 반복적으로 멈출 수 있음

### Step 12. 수거 장치 제어

구현:
- 그리퍼/흡입기 노드 작성
- 집기 시작/정지 명령
- 성공 여부 확인

완료 기준:
- 단일 쓰레기 반복 수거 성공

### Step 13. 임무 상태기계(FSM)

추천 상태:

1. `IDLE`
2. `PATROL`
3. `DETECT_TRASH`
4. `APPROACH_TRASH`
5. `ALIGN`
6. `PICKUP`
7. `VERIFY`
8. `MOVE_TO_BIN`
9. `DROP`
10. `RECOVERY`

완료 기준:
- 한 번의 수거 사이클 자동 수행

### Step 14. 실패 복구

반드시 넣을 것:
- GPS 튐
- 센서 timeout
- stuck detection
- 집기 실패 재시도
- emergency stop

## 7. 추천 ROS2 패키지 구조

```bash
~/autonomy_ws/src/
├── turtle_description
├── turtle_bringup
├── turtle_base
├── turtle_localization
├── turtle_nav
├── turtle_perception
├── turtle_pickup
├── turtle_task
└── turtle_eval
```

패키지 역할:

- `turtle_description`: URDF, TF
- `turtle_bringup`: 센서 및 드라이버 launch
- `turtle_base`: 모터, 엔코더, `/cmd_vel`, `/odom`
- `turtle_localization`: EKF, GPS 융합
- `turtle_nav`: Nav2 설정
- `turtle_perception`: 쓰레기 탐지
- `turtle_pickup`: 집기 장치 제어
- `turtle_task`: 상태기계
- `turtle_eval`: 로그와 성능 평가

## 11. 개발 원칙

- 처음부터 모든 걸 동시에 붙이지 않는다.
- 위치추정, 주행, 탐지, 집기를 분리해서 검증한다.
- 실외 공터에서는 GPS 중심 설계를 우선한다.
- D435i는 근거리 정밀 작업에 먼저 사용한다.
- 항상 rosbag를 남긴다.
- 문제가 생기면 `좌표계 -> 보정 -> timestamp -> 센서 품질` 순서로 점검한다.
