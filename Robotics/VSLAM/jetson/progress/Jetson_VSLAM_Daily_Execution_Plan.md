# Jetson VSLAM 일일 실행 계획

## 결론

- 지금 시점의 일일 계획은 `Jetson`에서 `D435i + RTAB-Map` 기준선을 재현 가능하게 만드는 데 집중해야 한다.
- 즉, 하루 단위 목표는 "많이 하기"보다 **기준선 하나를 확실하게 고정하고 증빙을 남기는 것**이어야 한다.
- 아래 계획은 현재 상태를 기준으로 한 추천 순서이며, 실제 진행 중 블로커가 생기면 다음 날 계획은 조정한다.

---

## 1. 운영 원칙

1. 하루 목표는 하나의 핵심 산출물만 본다.
2. `Jetson`에서 실제로 돌려본 결과만 기록한다.
3. GUI 확인이 필요한 작업은 직접 연결 상태에서 진행한다.
4. 하루가 끝나면 "무엇이 재현됐는가"를 반드시 남긴다.

---

## 2. 일일 계획 큰 흐름

### Day 1. Jetson 기준선 인벤토리 정리

목표:

- `Jetson` 시스템 상태를 먼저 정리한다.

작업:

- `JetPack`, `L4T`, `uname -m`, `ROS_DISTRO`, 디스크 여유, Docker 상태 확인
- `Jetson` 작업 경로와 워크스페이스 구조 점검
- 직접 연결과 `SSH` 작업 분담 기준 메모

남길 것:

- 환경 정보 메모
- 자주 쓰는 기본 명령 모음

완료 기준:

- "지금 이 Jetson이 어떤 상태인지"가 문서로 남아 있다.

### Day 2. D435i Native Bring-up 재현

목표:

- `Jetson`에서 `D435i`가 native ROS 2 환경에서 안정적으로 뜨는지 재확인한다.

작업:

- `realsense2_camera` launch
- `ros2 topic list`
- color/depth/IMU 토픽 확인
- `USB 3.x` 여부, `udev rules`, 장치 충돌 여부 확인

남길 것:

- launch 명령
- topic 목록
- 장치 인식 화면/로그

완료 기준:

- `D435i` bring-up 성공 여부가 다시 확인된다.

### Day 3. 저부하 기준선 확인

목표:

- `Jetson`에서 가장 안전한 저부하 실행 기준선을 확인한다.

작업:

- depth-only 저대역폭 세팅 확인
- color/depth 해상도별 체감 차이 기록
- `ros2 topic hz` 또는 대체 측정으로 토픽 흐름 확인

남길 것:

- 현재 Jetson에서 가장 안정적인 카메라 기본 세팅

완료 기준:

- "Jetson에서 최소한 이 세팅은 안정적"이라는 기준이 하나 생긴다.

### Day 4. RTAB-Map 1차 기동

목표:

- `Jetson`에서 `RTAB-Map`을 실제로 띄우고 기본 동작을 본다.

작업:

- `D435i RGB-D` launch
- `RTAB-Map` 경량 launch
- `rtabmap_viz` 중심으로 맵과 odometry 상태 확인

남길 것:

- 실행 명령
- `quality`, `delay`, `update time` 로그 일부
- 첫 성공 캡처

완료 기준:

- `Jetson`에서 `RTAB-Map`이 최소 1회 정상 기동한다.

### Day 5. RTAB-Map 후보 세팅 비교

목표:

- `Jetson` 기준 후보 세팅을 비교한다.

비교 대상 예시:

1. `640x480x15`
2. `424x240x15`
3. IMU ON/OFF
4. `DetectionRate 2/3`

남길 것:

- 후보별 로그
- 체감 부드러움 비교
- 너무 무거운 조합 제외 사유

완료 기준:

- `Jetson` 기준 후보 2개 이하로 압축된다.

### Day 6. 기준 세팅 고정

목표:

- `Jetson`에서 쓸 기본 세팅 1개를 고른다.

작업:

- 후보 재시험
- 짧은 실내 동선 반복
- 재실행 시 재현성 확인

남길 것:

- "현재 Jetson 기준 권장 세팅" 문장 1개
- 기준 로그와 캡처

완료 기준:

- 이후 모든 실험의 기본 출발점이 되는 세팅이 고정된다.

### Day 7. 실행 절차 문서화

목표:

- 다른 날 다시 와도 그대로 따라할 수 있게 실행 절차를 고정한다.

작업:

- 프로세스 정리 명령
- 카메라 실행 명령
- `RTAB-Map` 실행 명령
- 실패 시 먼저 볼 항목 정리

남길 것:

- `Jetson` 전용 실행 절차 문서
- 필요하면 wrapper 스크립트

완료 기준:

- "처음부터 다시 띄우는 방법"이 문서와 스크립트로 남아 있다.

### Day 8. 성능/운영 체크

목표:

- `Jetson` 자원 한계와 운영 리스크를 확인한다.

작업:

- `CPU`, `memory`, 필요하면 `temperature` 관찰
- GUI가 성능에 미치는 영향 비교
- `SSH only`와 직접 연결 작업의 차이 메모

남길 것:

- 운영 시 주의사항
- 병목 후보

완료 기준:

- 이후 통합 단계에서 피해야 할 조합이 정리된다.

### Day 9. Docker 또는 재현 환경 정리

목표:

- 필요하면 Docker 기반 실행 가능성을 검토한다.

작업:

- Jetson Docker 상태 확인
- 컨테이너에서 장치 접근 가능성 검토
- 지금은 native가 맞는지, Docker가 맞는지 판단 메모

남길 것:

- "현재는 native 우선" 또는 "Docker 전환 가능" 판단

완료 기준:

- 실행 환경 전략이 정리된다.

### Day 10. 다음 단계 연결 준비

목표:

- `Jetson VSLAM baseline`을 이후 센서 융합/자율주행 단계와 연결한다.

작업:

- `encoder`, `external IMU`, `GPS`, `Nav2`로 이어지는 확장 포인트 정리
- 현재 baseline이 어디까지 검증됐는지 문장으로 명확히 남기기

남길 것:

- 다음 스프린트 연결 메모

완료 기준:

- `Jetson` 작업이 단발성 실험이 아니라 다음 단계로 이어질 수 있는 상태가 된다.

---

## 3. 당장 오늘부터 적용할 실행 순서

지금 시점에서 가장 추천하는 실제 순서는 아래다.

1. Day 1 성격의 시스템 인벤토리 정리
2. Day 2 성격의 `D435i` native bring-up 재현
3. Day 4 성격의 `RTAB-Map` 1차 기동
4. Day 5~6 성격의 기준 세팅 압축 및 고정

즉, 지금은 `Docker`, `Nav2`, `robot_localization`을 바로 건드리기보다
**`Jetson`에서 `D435i + RTAB-Map` baseline을 먼저 재현 가능하게 만드는 것**이 더 중요하다.

---

## 4. 매일 공통으로 남길 체크리스트

- 오늘 어떤 작업을 `SSH`로 했는가
- 오늘 어떤 작업을 직접 화면으로 했는가
- `D435i`는 정상 인식됐는가
- `device busy`, `udev`, `USB`, `GUI`, `CPU` 문제는 있었는가
- 오늘 기준으로 가장 안정적인 실행 조합은 무엇이었는가
- 내일 바로 이어서 할 1순위는 무엇인가

---

## 5. 한 줄 요약

- `Jetson` 일일 계획의 핵심은 "큰 기능을 많이 붙이는 것"이 아니라,
  **`D435i + RTAB-Map` baseline을 Jetson에서 안정적으로 굴리는 기준선을 확정하는 것**이다.
