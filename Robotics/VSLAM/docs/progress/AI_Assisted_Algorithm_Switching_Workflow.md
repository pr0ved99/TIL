# AI Assisted Algorithm Switching Workflow

## 결론

- `AI로 논문을 찾아서 검증된 알고리즘 후보를 좁히는 방법`은 충분히 쓸 만한 전략이다.
- 다만 `AI 추천 = 바로 갈아타기`로 가면 위험하다.
- 가장 실용적인 방식은 `현재 baseline 유지 -> AI로 후보 조사 -> 코드/재현성 확인 -> 1개만 비교 실험` 순서다.

## 목적

- 현재 알고리즘이 충분히 맞는지 판단한다.
- 새 알고리즘으로 갈아탈 가치가 있는지 객관적으로 본다.
- 논문 이름만 유명한 알고리즘이 아니라, 실제로 설치 가능하고 재현 가능한 알고리즘을 고른다.

## 추천 순서

1. 현재 baseline을 유지한다.
   - 예: 지금은 `RTAB-Map`이 baseline이다.
2. AI로 후보 알고리즘을 3~5개 조사한다.
3. 각 후보의 입력 조건을 정리한다.
   - `monocular`, `stereo`, `RGB-D`, `IMU 필수 여부`
4. 공개 코드와 최근 유지보수 상태를 확인한다.
5. 현재 하드웨어와 ROS2 환경에 맞는 후보만 남긴다.
6. 그중 1개만 추가 실험한다.
7. baseline과 같은 조건에서 비교한다.
   - `ATE`, `RPE`, `FPS`, `CPU`, `메모리`, `설치 난이도`

## 왜 이렇게 해야 하나

- 논문이 좋아 보여도, 현재 환경에서 안 돌아가면 의미가 없다.
- AI가 논문을 잘 찾더라도, 실제 코드 품질과 재현성까지 대신 보장해주지는 않는다.
- 한 번에 여러 알고리즘으로 갈아타면, 무엇 때문에 좋아졌는지 나빠졌는지 판단이 안 된다.

## 비교 기준

- 공개 코드가 있는가
- 최근에도 빌드/실행 사례가 있는가
- Ubuntu 22.04 / ROS2와 연결 가능한가
- D435i 입력(`RGB-D`)을 직접 지원하는가
- IMU가 필수인지 선택인지
- 실내/실외 어느 환경에 강한가
- 성능 비교가 가능한가
  - `ATE`
  - `RPE`
  - `FPS`
  - `CPU/GPU`
  - `메모리`

## 현재 프로젝트 기준 추천

- 지금은 `RTAB-Map`을 baseline으로 유지한다.
- 비교 후보는 `코드가 있고 재현 사례가 많은 것`만 본다.
- 가장 현실적인 다음 후보는 `ORB-SLAM3 RGB-D` 정도로 좁혀서 보는 게 맞다.

## 한 줄 요약

- `AI는 후보 조사 도구로는 좋다.`
- `최종 선택은 baseline 비교 실험으로 결정해야 한다.`
