# 공터에서 쓰레기를 줍는 자율주행 로봇 개발 단계별 로드맵

## 0. 결론

- 지금 너희 프로젝트는 `VSLAM 단독 기반 로봇`이 아니라 `GPS + 엔코더 + IMU + D435i + Nav2 + 쓰레기 탐지 + 수거 장치`를 합친 실외 자율주행 시스템으로 보는 것이 맞다.
- 공터처럼 특징점이 부족한 환경에서는 `카메라 기반 VSLAM`을 주 위치추정 수단으로 두기보다, `GPS 기반 전역 위치 + 엔코더/IMU 기반 로컬 오도메트리` 구조로 가는 것이 훨씬 현실적이다.
- D435i는 전역 위치추정보다 `근거리 장애물 확인`, `쓰레기 탐지`, `마지막 정밀 접근`에 쓰는 것이 더 적합하다.

## 1. 먼저 큰 그림을 이해하기

직관:
자율주행이 완성된다는 것은 "로봇이 스스로 돌아다닌다"가 끝이 아니다. 자기 위치를 알고, 목적지를 향해 이동하고, 쓰레기를 발견하고, 가까이 가서, 집고, 다시 이동할 수 있어야 한다.

핵심 개념:
- `Localization(위치추정)`: 로봇이 현재 어디 있는지 아는 것
- `Navigation(내비게이션)`: 목적지까지 경로를 짜고 실제로 가는 것
- `Perception(인지)`: 카메라로 쓰레기나 장애물을 인식하는 것
- `Manipulation(조작)`: 집게나 흡입기로 물체를 집는 것
- `Mission Control(임무 제어)`: 탐색, 접근, 수거, 복귀 순서를 관리하는 것

즉, 최종 시스템은 아래처럼 나뉜다.

```text
위치추정 + 주행 + 인지 + 집기 + 임무제어
```

## 2. 지금 가진 장비 기준 현실적인 해석

현재 확보한 장비:

- `D435i`
- `엔코더 달린 모터`
- `GPS`

의미:
- `D435i`: RGB 영상, depth, IMU를 제공
- `엔코더 모터`: 바퀴 회전량으로 오도메트리 계산 가능
- `GPS`: 실외 공터에서 전역 위치 추정 가능

중요한 판단:
- 공터는 특징점이 부족할 가능성이 높다.
- 따라서 `특징점 기반 VSLAM으로 방향/위치를 주력 보정`하는 설계는 불안정할 수 있다.
- 이 조건에서는 `GPS + 엔코더 + IMU`가 중심이고, `D435i`는 보조 센서로 쓰는 것이 맞다.

## 3. 추천 전체 아키텍처

가장 실용적인 추천 구조는 아래와 같다.

```text
GPS --------------------------> 전역 위치
엔코더 + IMU -----------------> 로컬 오도메트리(EKF)
D435i ------------------------> 근거리 인지 / 쓰레기 탐지 / 마지막 접근
전역 위치 + 로컬 위치 ---------> Nav2
카메라 탐지 결과 -------------> 접근 목표 생성
수거 장치 제어 ---------------> 집기 동작
상태기계 ---------------------> 전체 미션 제어
```

좌표계 역할도 분리하는 것이 좋다.

- `map`: 전역 기준 좌표계
- `odom`: 부드러운 로컬 기준 좌표계
- `base_link`: 로봇 본체 기준 좌표계

권장 역할:
- `GPS 포함 위치추정`: `map` 기준 위치 보정
- `엔코더 + IMU + EKF`: `odom -> base_link`
- `D435i`: 장애물/쓰레기/정밀 접근용

## 4. 왜 VSLAM을 주력으로 두지 않는가

직관:
VSLAM은 특징점이 잘 보이는 환경에서 강하다. 하지만 공터, 흙바닥, 잔디, 단조로운 야외 환경은 반복 추적할 특징이 부족할 수 있다.

핵심 개념:
- `Feature(특징점)`: 영상에서 다시 찾기 쉬운 점
- `Scale Drift`: 시간이 지나며 거리 비율이 틀어지는 현상
- `Outlier`: 잘못 매칭된 관측값

공터 환경의 문제:
- 바닥 패턴이 단조로움
- 조명 변화가 큼
- 햇빛 때문에 depth 품질 저하 가능
- 멀리 있는 물체가 많고 가까운 특징이 적음

결론:
- `VSLAM`: 선택적 보조
- `GPS + 엔코더 + IMU`: 주 위치추정

## 5. 개발 단계 전체 개요

자율주행 완료까지는 아래 순서로 가는 것이 좋다.

1. 로봇을 실제로 움직이게 만든다.
2. ROS2에서 센서 데이터를 안정적으로 읽는다.
3. 좌표계와 TF를 정리한다.
4. 엔코더 기반 오도메트리를 만든다.
5. IMU와 합쳐 로컬 위치추정을 안정화한다.
6. GPS를 붙여 전역 위치추정을 만든다.
7. Nav2로 목표점 이동을 성공시킨다.
8. D435i로 쓰레기 탐지를 붙인다.
9. 쓰레기 위치를 로봇 좌표계로 변환한다.
10. 마지막 접근 행동을 만든다.
11. 수거 장치를 제어한다.
12. 전체 미션 상태기계를 통합한다.
13. 실패 복구와 성능 평가를 추가한다.

## 9. 현재 범위 이후 단계별 상세 진행방안

### Stage A. 쓰레기 인지 추가

직관:
기본 주행이 된다고 해서 임무가 완료되는 것은 아니다. 이제부터는 "무엇이 쓰레기인지"를 찾아야 한다.

구현:
- 쓰레기 종류 정의
- 탐지 기준 정리
- D435i RGB 영상 기반 detector 연결
- bounding box 또는 segmentation 결과 출력

완료 기준:
- 화면에서 쓰레기 후보를 안정적으로 찾음
- 탐지 confidence를 기록할 수 있음

### Stage B. 쓰레기 위치를 로봇 좌표계로 변환

직관:
화면에서 찾는 것과 실제로 갈 수 있는 것은 다르다. 탐지 결과를 로봇 기준 위치로 바꿔야 한다.

구현:
- depth와 탐지 결과 결합
- 쓰레기 후보의 3D 위치 계산
- `camera_link -> base_link` 변환 적용
- 후보 위치의 안정성 확인

완료 기준:
- 쓰레기의 로봇 기준 위치 `(x, y, z)`를 반복적으로 계산 가능
- 깊이 결측과 오탐을 분리해서 볼 수 있음

### Stage C. 마지막 정밀 접근

직관:
GPS와 Nav2는 근처까지 가는 데 좋고, 마지막 수십 cm 정렬은 카메라가 더 잘한다.

구현:
- 쓰레기 앞 임시 정지점 생성
- 저속 접근 제어
- yaw 정렬
- 마지막 정밀 정렬

완료 기준:
- 쓰레기 앞에 반복적으로 멈출 수 있음

### Stage D. 수거 장치 제어

구현:
- 그리퍼/흡입기 노드 작성
- 집기 시작/정지 명령
- 성공 여부 확인

완료 기준:
- 단일 쓰레기 반복 수거 성공

### Stage E. 임무 상태기계(FSM)

직관:
이제부터는 단순 기능 성공보다, 순찰부터 수거까지의 순서 제어가 중요하다.

추천 상태:

1. `IDLE`
2. `PATROL`
3. `DETECT_TRASH`
4. `APPROACH_TRASH`
5. `ALIGN`
6. `PICKUP`
7. `VERIFY`
8. `MOVE_TO_BIN`
9. `DROP`
10. `RECOVERY`

완료 기준:
- 한 번의 수거 사이클 자동 수행

### Stage F. 실패 복구와 실외 반복 튜닝

직관:
실외 공터에서는 한 번 성공보다 여러 번 반복 성공하는 것이 훨씬 중요하다.

반드시 넣을 것:
- GPS 튐
- 센서 timeout
- stuck detection
- 집기 실패 재시도
- emergency stop

완료 기준:
- 순찰 -> 탐지 -> 접근 -> 수거 -> 복귀 흐름이 반복적으로 성공
- 실패 원인이 로그로 추적 가능

## 10. 추천 ROS2 패키지 구조

```bash
~/autonomy_ws/src/
├── turtle_description
├── turtle_bringup
├── turtle_base
├── turtle_localization
├── turtle_nav
├── turtle_perception
├── turtle_pickup
├── turtle_task
└── turtle_eval
```

패키지 역할:

- `turtle_description`: URDF, TF
- `turtle_bringup`: 센서 및 드라이버 launch
- `turtle_base`: 모터, 엔코더, `/cmd_vel`, `/odom`
- `turtle_localization`: EKF, GPS 융합
- `turtle_nav`: Nav2 설정
- `turtle_perception`: 쓰레기 탐지
- `turtle_pickup`: 집기 장치 제어
- `turtle_task`: 상태기계
- `turtle_eval`: 로그와 성능 평가

## 11. 현재 범위 이후 거시 일정 틀

이 일정은 `현재 스프린트 + 현재 Backlog`가 끝난 뒤를 기준으로 한 거시 일정이다.

### Phase 1. 인지 기반 확장

- 기간: `1~2주`
- 목표: 쓰레기 탐지와 후보 위치 계산

핵심 결과물:
- 쓰레기 detector
- 탐지 결과 로그
- 3D 위치 계산 초안

### Phase 2. 정밀 접근

- 기간: `1~2주`
- 목표: 쓰레기 앞 정지점 생성과 마지막 접근

핵심 결과물:
- 접근 제어 로직
- yaw 정렬
- 저속 정밀 접근 검증 로그

### Phase 3. 수거 장치 연동

- 기간: `1~2주`
- 목표: 집기/흡입기 제어와 수거 성공 판정

핵심 결과물:
- pickup 인터페이스
- 성공/실패 판정
- 반복 집기 테스트 기록

### Phase 4. 미션 통합

- 기간: `1주`
- 목표: 순찰 -> 탐지 -> 수거 -> 복귀 자동화

핵심 결과물:
- FSM
- 상태 전이 로그
- 단일 수거 사이클 데모

### Phase 5. 실외 검증과 개선

- 기간: `2주 이상 반복`
- 목표: 성공률을 올리고 실패 복구를 안정화

핵심 결과물:
- 반복 실험 로그
- 실패 유형별 대응 표
- 최종 성능 평가표

## 12. 최종 목표 달성 체크포인트

아래 체크포인트가 차례로 만족되어야 최종 목표 달성으로 본다.

1. 지정한 공터를 자동 순찰할 수 있다.
2. 쓰레기 후보를 탐지할 수 있다.
3. 쓰레기 위치를 로봇 기준으로 계산할 수 있다.
4. 쓰레기 앞까지 안정적으로 접근할 수 있다.
5. 쓰레기를 집을 수 있다.
6. 집은 뒤 복귀 또는 다음 순찰로 이어질 수 있다.
7. 위 과정이 반복적으로 성공한다.

## 13. 다음 백로그 생성 기준

앞으로 새 백로그를 만들 때는 아래 기준으로 쪼개는 것이 좋다.

### 기준 1. 최종 목표 체인 기준

```text
탐지 -> 위치 계산 -> 접근 -> 집기 -> 복귀 -> 반복 성공률 개선
```

### 기준 2. 각 단계별 산출물 기준

- 입력 토픽
- 중간 결과 메시지
- 제어 로직
- 검증 로그
- 성공/실패 기준

### 기준 3. 한 스프린트에 하나의 검증 목표만 넣기

예:
- 이번 스프린트: `탐지 성공`
- 다음 스프린트: `3D 위치 계산 성공`
- 그 다음 스프린트: `마지막 접근 성공`

## 14. 예시 백로그 묶음 템플릿

나중에 새 백로그를 만들 때는 아래 묶음을 기준으로 확장하면 된다.

### 백로그 묶음 A. 쓰레기 탐지

- 쓰레기 클래스 정의
- 데이터 수집 기준 정리
- detector 연결
- 탐지 결과 메시지 정의
- confidence 로그 기록

### 백로그 묶음 B. 쓰레기 위치 계산

- depth와 bounding box 결합
- 3D 위치 계산
- `camera_link -> base_link` 변환
- 결측치와 노이즈 처리

### 백로그 묶음 C. 마지막 접근

- 목표 정지점 생성
- 저속 접근 제어
- yaw 정렬
- 접근 실패 recovery

### 백로그 묶음 D. 수거 장치

- pickup 인터페이스
- 성공 판정
- 실패 재시도

### 백로그 묶음 E. 임무 상태기계

- 상태 정의
- 상태 전이 조건
- timeout 처리
- recovery 경로

## 16. 개발 원칙

- 처음부터 모든 걸 동시에 붙이지 않는다.
- 위치추정, 주행, 탐지, 집기를 분리해서 검증한다.
