# 스프린트 실행 기준과 백로그 문서화 정리

## 0. 결론

- 실제 실행은 `현재 스프린트에 올라간 항목만` 진행한다.
- `Backlog`에 있는 항목은 당장 구현 대상으로 보지 않고, 이후 스프린트 준비를 위한 `문서/참고 자료`로 관리한다.
- 즉, 지금 당장은 `D435i depth 확인`과 `Jetson Docker 환경 확인`이 실행 대상이고, `URDF/xacro`, `Gazebo`, `위치추정`, `Nav2`는 문서와 설계 기준으로 남긴다.

## 1. 운영 원칙

직관:
해야 할 일과 나중에 할 일을 섞어두면 집중이 깨지고, 스프린트가 무거워진다.

이번 프로젝트에서는 아래처럼 나눈다.

- `Sprint`: 이번 주 실제로 손대는 실행 항목
- `Backlog`: 다음 단계 준비를 위한 설계, 문서, 구조 정리 항목

핵심 원칙:

1. 이번 주 작업은 스프린트 항목만 본다.
2. Backlog 항목은 구현보다 문서화와 기준 정리에 우선 사용한다.
3. Backlog에서 바로 할 수 있더라도, 스프린트에 올리기 전까지는 참고용으로만 본다.

## 2. 지금 스프린트에서 실제 실행할 항목

현재 스프린트 기준으로 바로 실행하는 대상은 아래다.

### D435i 확인

- `S14P31C205-59` `[EM] D435i 스트림 구동 및 depth 토픽 확인`
- `S14P31C205-60` `[EM] D435i depth 시각화 구현`
- `S14P31C205-61` `[EM] depth 시각화 캡처 및 검증 기록 정리`

### Jetson Docker 환경

- `S14P31C205-63` `[INFRA] Jetson Docker 설치 및 기본 실행 환경 확인`
- `S14P31C205-64` `[INFRA] Jetson에서 컨테이너 실행 및 장치 검증`
- `S14P31C205-65` `[INFRA] Jetson Docker 실행 절차 문서화`

## 3. 지금 스프린트에서 우선순위

가장 추천하는 실행 순서는 아래다.

1. `59` D435i 스트림 구동 및 depth 토픽 확인
2. `60` D435i depth 시각화 구현
3. `61` depth 시각화 캡처 및 검증 기록 정리
4. `63` Jetson Docker 설치 및 기본 실행 환경 확인
5. `64` Jetson에서 컨테이너 실행 및 장치 검증
6. `65` Jetson Docker 실행 절차 문서화

이 순서를 추천하는 이유:

- D435i는 이미 손에 있는 센서라 바로 검증 가능하다.
- depth 토픽이 정상인지 먼저 알아야 이후 자율주행과 근거리 인지 활용 여부를 판단할 수 있다.
- Jetson Docker는 이후 실행 환경의 기반이므로 센서 확인 다음에 정리하는 것이 좋다.

## 4. Backlog는 어떻게 다룰 것인가

Backlog는 당장 구현하지 않는 대신, 아래 역할로 사용한다.

### 4-1. 설계 기준 문서

예:

- URDF/xacro 구조
- Gazebo 시뮬레이션 순서
- 엔코더/IMU/GPS 위치추정 체인
- Nav2 도입 순서

### 4-2. 다음 스프린트 후보 정리

예:

- `로봇 모델링`
- `위치추정`
- `자율주행`

### 4-3. 선행 개념 학습 자료

예:

- `robot_state_publisher`
- `odom -> base_link`
- `navsat_transform_node`
- `robot_localization`

## 5. 지금 Backlog에 있는 항목은 어떤 의미인가

현재 Backlog에 있는 항목은 `실행 대기 작업`이 아니라, 아래 순서의 `다음 단계 개발 로드맵`으로 본다.

1. `로봇 모델링`
   - URDF/xacro
   - RViz2 display
   - Gazebo 차동구동
2. `위치추정`
   - 엔코더 odom
   - IMU 융합
   - GPS 기반 전역 위치추정
3. `자율주행`
   - Nav2 waypoint
   - costmap
   - D435i 기반 근거리 장애물 입력

즉, Backlog는 "언젠가 할 일 목록"이 아니라, "다음 스프린트들에서 이 순서로 확장할 기술 설계"로 이해하면 된다.

## 6. 스프린트가 끝난 뒤 Backlog를 어떻게 옮길 것인가

이번 스프린트가 끝나면 아래 기준으로 다음 후보를 고른다.

### 다음 스프린트 1순위 후보

- `[EM] 로봇 링크/조인트 구조 초안 작성`
- `[EM] base_link, 휠, D435i, GPS, IMU xacro 작성`
- `[EM] RViz2 display launch 및 robot_state_publisher 설정`

### 그 다음 후보

- `[EM] diff drive 구동 파라미터 정리`
- `[EM] Gazebo spawn 및 /cmd_vel 연동`
- `[EM] 직진/회전 시뮬레이션 검증`

즉, 다음 스프린트는 `URDF/xacro -> RViz2 -> Gazebo` 순서가 가장 자연스럽다.

## 7. 문서화 기준

스프린트 항목을 수행할 때는 반드시 아래 자료를 남긴다.

### D435i 관련

- 실행 명령
- 사용한 launch 옵션
- `ros2 topic list` 결과
- depth 관련 토픽 이름
- RViz2 또는 시각화 캡처
- 동작 성공/실패 여부
- 문제 발생 시 원인 가설

### Jetson Docker 관련

- Jetson OS/JetPack 정보
- `docker --version`
- `docker info`
- 실행한 컨테이너 이미지 이름
- 성공한 실행 명령
- 장치 전달 여부
- 문제와 해결 기록

## 8. 지금 바로 적용할 실무 규칙

- Jira를 볼 때는 `Sprint`만 작업 대상으로 본다.
- `Backlog`는 스프린트 계획 전까지는 문서와 기준 정리용으로 본다.
- 새로운 구현 아이디어가 생겨도 바로 Backlog 실행으로 가지 않고, 먼저 문서에 정리한다.
- 이번 주는 `D435i`, `Jetson Docker`에 집중한다.

## 9. 한 줄 요약

- `지금 한다` = 스프린트
- `지금은 안 하지만 남겨둔다` = Backlog 문서
- `다음 스프린트 후보` = URDF/xacro -> Gazebo -> 위치추정 -> Nav2
