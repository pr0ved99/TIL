# Jira Convention Guide

## 1. 개발 방법론

- 애자일 스크럼 기반, 1주 단위 스프린트로 운영한다.

## 2. 스프린트 사이클 (1주)

| 요일 | 활동 | 핵심 내용 |
| --- | --- | --- |
| **월요일** | 스프린트 플래닝 | 제품 백로그에서 스토리 선정, 스토리 포인트 기반 업무량 결정, 개인별 태스크 분배 |
| **화~목** | 스프린트 진행 | 개발 수행, 데일리 스크럼, 칸반 보드 상태 업데이트 |
| **금요일** | 리뷰 + 회고 | 결과물 검토, 번다운 차트 확인, 회고 결과물 작성 및 제출 |

## 3. 이슈 계층 구조

```text
에픽 (Epic)
 └── 스토리 (Story)           ← 제품 백로그 단위, 사용자 관점 요구사항
      └── 태스크 (Task)       ← 개인별 구체적 작업 단위
```

### 연결 규칙

- **서브태스크(Sub-task)는 사용하지 않는다.**
  - 번다운 차트, 리포트에 포함되지 않아 인사이트를 얻기 어렵기 때문
- 스토리와 태스크는 **Ctrl+K -> 링크(Link)**로 계층 관계를 연결한다.
- 하나의 스토리에서 FE/BE 태스크가 각각 파생될 수 있다.

### 예시

```text
[Epic] 회원관리
 ├── [Story] 사용자는 서비스에 가입하기 위하여 회원가입을 할 것이다.
 │    ├── [Task] [FE] 회원가입 화면 구현
 │    └── [Task] [BE] 회원가입 API 개발
 └── [Story] 사용자는 탈퇴를 원하면 탈퇴할 수 있을 것이다.
      ├── [Task] [FE] 탈퇴 확인 모달 구현
      └── [Task] [BE] 회원 탈퇴 API 개발
```

## 4. 이슈 작성 컨벤션

### 4-1. 에픽 (Epic)

서비스의 큰 기능 단위다. 도메인 또는 기능 모듈 기준으로 분류한다.

**네이밍**: `기능 도메인명`

예:
- `회원관리`
- `라이브 스트리밍`
- `채팅`
- `녹화 관리`

### 4-2. 스토리 (Story)

사용자 관점에서 비개발자 언어로 작성한 요구사항이다. 개발자 중심으로 쓰면 구현 편의 위주로 흘러갈 수 있으므로, 반드시 **사용자 관점**으로 작성한다.

**템플릿**:

```text
[대상]은(는) [목적]하기 위하여 [활동/작업/기능]할 것이다.
```

**예시**:

- 사용자는 서비스를 이용하기 위하여 회원가입을 할 것이다.
- 스트리머는 방송을 시작하기 위하여 스튜디오를 생성할 것이다.
- 시청자는 의견을 전달하기 위하여 실시간 채팅을 할 것이다.

**필수 항목**:

| 항목 | 설명 |
| --- | --- |
| 우선순위 | Highest / High / Medium / Low / Lowest |
| 스토리 포인트 | 피보나치 수열 기반 (1, 2, 3, 5, 8, 13) |
| 에픽 링크 | 소속 에픽 연결 |
| 담당자 | 없어도 됨 (팀 상황에 따라 유동적) |

### 4-3. 태스크 (Task)

스토리를 구현하기 위한 개인별 구체적 작업이다.

**네이밍**: `[역할] 작업 내용`

| 접두어 | 역할 |
| --- | --- |
| `[FE]` | 프론트엔드 |
| `[BE]` | 백엔드 |
| `[INFRA]` | 인프라 |
| `[AI]` | AI |
| `[공통]` | 전체 공통 |
| `[EM]` | 임베디드 |

**예시**:

- `[BE] 회원가입 API 개발`
- `[FE] 로그인 화면 구현`
- `[INFRA] Docker Compose 환경 설정`

**필수 항목**:

| 항목 | 설명 |
| --- | --- |
| 우선순위 | Highest / High / Medium / Low / Lowest |
| 스토리 포인트 | 피보나치 수열 기반 (1, 2, 3, 5, 8, 13) |
| 담당자 | 개인별 지정 |
| 링크 | 상위 스토리와 Ctrl+K로 연결 |

## 5. 스토리 포인트 규칙

### 기본 원칙

- 시간 대신 **구현 난이도(크기 + 복잡성)**를 상대적으로 측정하는 단위다.
- **피보나치 수열**을 사용한다: `1, 2, 3, 5, 8, 13`
- 범위는 **1~13**으로 제한한다.
- 팀 내 **기준 스토리**를 하나 정하고, 나머지를 상대 비교하여 산정한다.

### 포인트 가이드

| 포인트 | 난이도 | 설명 | 예시 |
| --- | --- | --- | --- |
| **1** | 매우 쉬움 | 단순 수정, 설정 변경 | 환경변수 추가, 텍스트 수정 |
| **2** | 쉬움 | 간단한 기능 구현 | 단순 CRUD 1개, 정적 페이지 |
| **3** | 보통 | 일반적인 기능 구현 | API 1개 + 화면 연동 |
| **5** | 약간 어려움 | 복잡한 로직 포함 | 인증 흐름, 복잡한 폼 처리 |
| **8** | 어려움 | 여러 컴포넌트 연동 | 실시간 통신, 파일 업로드 |
| **13** | 매우 어려움 | 대규모 기능, 높은 불확실성 | 새 아키텍처 설계, 외부 연동 |

### 산정 방법

1. 제품 백로그 전체를 먼저 도출한다.
2. **기준 스토리**를 하나 잡는다. 예: `"회원가입" = 3`
3. 나머지 스토리를 기준 대비 상대적으로 비교하여 포인트를 부여한다.
4. 플래닝 포커 등을 통해 팀원 간 합의로 결정한다.
5. 정답이 아니라 **팀의 소통과 합의**가 핵심이다.

## 6. 우선순위 기준

| 레벨 | 의미 | 기준 |
| --- | --- | --- |
| **Highest** | 즉시 처리 | 이것 없으면 다른 작업 진행 불가 (선행 의존성) |
| **High** | 이번 스프린트 필수 | 핵심 기능, MVP에 반드시 포함 |
| **Medium** | 이번 스프린트 권장 | 있으면 좋지만, 밀려도 치명적이지 않음 |
| **Low** | 여유 있을 때 | 부가 기능, 개선 사항 |
| **Lowest** | 백로그 대기 | 나중에 해도 되는 것 |

## 7. 워크플로우 (칸반 상태)

```text
To Do  ->  In Progress  ->  Done
```

| 상태 | 설명 |
| --- | --- |
| **To Do** | 이번 스프린트에 할 일로 선정됨, 아직 미착수 |
| **In Progress** | 현재 작업 중 |
| **Done** | 완료 (리뷰 통과, 머지 완료) |

## 8. 제품 백로그 관리

- 제품 백로그는 **우리가 만들려는 서비스/제품의 요구사항 목록**이다. 개인 할 일이 아니다.
- 우선순위가 매겨진 스토리 목록으로 관리한다.
- 스토리 포인트가 반드시 등록되어야 한다.
- 스프린트 플래닝 시, 우선순위가 높은 순서대로 스프린트 백로그에 가져온다.

## 9. 스프린트 리뷰 & 회고

### 리뷰 (금요일)

- 완료된 결과물을 검토한다.
- 계획 단계에서 정의한 **완료 조건**과 실제 결과의 차이를 확인한다.
- **벨로시티** 확인: 완료된 스토리 포인트 총합 = 팀 생산성
- 리뷰 결과를 제품 백로그에 반영한다.

### 회고 (금요일)

- 스프린트 과정 + 협업 방식을 검토한다.
- 잘한 점 / 개선할 점 / 다음 스프린트에 시도할 것을 정리한다.
- **회고 결과물을 매주 금요일 제출**한다.

### 번다운 차트

- 리포트 기능에서 번다운 차트를 확인한다.
- 예쁘게 만들려 하지 말고, **실제 진행 상황 파악 도구**로 활용한다.

## 10. 핵심 요약

- 서브태스크는 쓰지 않는다. 리포트에 반영되지 않는다.
- 스토리와 태스크는 링크(Ctrl+K)로 연결한다.
- 스토리는 사용자 관점으로 작성한다.
- 스토리 포인트는 피보나치(1~13)로 잡고, 팀 합의로 결정한다.
- 매주 금요일 회고 결과물을 제출한다.
- 번다운 차트는 꾸미기용이 아니라 인사이트 도구로 활용한다.
