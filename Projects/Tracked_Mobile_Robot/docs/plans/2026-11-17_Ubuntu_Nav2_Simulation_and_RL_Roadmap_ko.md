## 1. 이번 방향과 완료의 의미

11/17 계획을 작성할 당시에 사용자는 Windows에서 작업하고 있었으며, **같은 노트북 내부 SSD를 약 절반 나누어 Ubuntu와 듀얼부팅**할 계획이라고 보고했다. 전환 시점은 미정이다. 기존 별도 Ubuntu SSD/Humble 기본 실행 이력은 과거 사실이며, 새 설치가 이미 있다는 뜻으로 사용하지 않는다.

**11/17 당시 추천:** 11/17~18 기존 일정 후 11/19 백업·환경 점검, 조건이 갖춰지면 11/20 설치, 11/21 ROS/Gazebo 점검. PCB 제작을 기다리지 않고 가상 센서·오도메트리·Nav2를 병행한다. 전환을 PCB 완성까지 미루지 않는 이유는 모델·토픽·TF·지도/경로 계획을 실물 없이 먼저 검증할 수 있기 때문이다.

목표 순서는 **재현 가능한 Nav2 기준선 → 선택적 강화학습 비교 → 준비된 하드웨어를 같은 인터페이스에 연결**이다. 강화학습 성공과 실물 자율주행은 이번 3주 일정의 보장 결과가 아니다. 사용자 요청은 계획 수립이며 오늘 설치·파티션 변경·구매·실물 구동을 실행하지 않았다.

## 2. 환경 전환 — 지금 정할 것과 설치 당일 확인할 것

### 2.1 읽기 전용으로 확인한 저장장치

11/17 Windows Get-Disk/Get-Volume/Get-Partition 조회: **WD Blue SN5000 1TB, GPT**, 디스크 1,000,204,886,016bytes. C: 999,056,994,304bytes 중 여유 773,254,856,704bytes(약773.3GB/720.2GiB), 사용 약225.8GB. EFI/MSR/C:/Recovery 파티션을 확인했다.

- Windows 약500GB, Ubuntu 약500GB 방향은 현재 사용량 기준 용량상 타당한 **배정 제안**이다. 남길 Windows 공간과 실제 축소 가능량을 설치 전 확인한다. 500GB와500GiB를 혼용하지 않는다.
- 여유 공간은 연속된 축소 가능 공간과 다르다. 아직 축소 가능량을 측정하거나 파티션을 변경하지 않았다.
- BitLocker 조회는 접근 거부로 실패했다. 뒤이어 나온 “연결된 볼륨 없음” 문구를 암호화 OFF의 근거로 사용하지 않는다.
- 9/8의256GB/별도500GB SSD 기록은 당시 상태다. 현재 장치 판단은 위 신규 조회를 우선한다.
- [읽기 전용 원자료](../../assets/logs/planning/2026-11-17_ubuntu_nav2_closeout/environment_readonly.json).

### 2.2 설치 진입 조건과 작업 공간

1. Git push와 별개로 미추적 파일·CAD·로컬 로그·개인 자료를 **내부 SSD 밖에 백업**하고 파일을 실제로 복원해 본다. 백업 장치 보유/백업 완료는 아직 미확인.
2. Windows 복구 방법과 BitLocker/장치 암호화 상태를 확인한다. 활성화돼 있으면 복구 정보를 안전하게 확보하고 공식 듀얼부팅 지침을 따른다. 키를 저장소/채팅에 기록하지 않는다.
3. 설치 USB·ISO 검증, UEFI 부팅, NVIDIA/네트워크의 Live USB 인식, 실제 축소 가능량을 확인한다. EFI/복구 파티션 보존 계획을 정한다.
4. 사용자가 준비된 절차로 설치하고 **Windows와 Ubuntu 모두 정상 부팅**해야 ENV-02 완료다. 조건이 남으면 날짜를 이월한다.
5. Ubuntu 작업용 Git checkout과 colcon build/install/log는 Linux 파일시스템에 둔다. NTFS의 Windows build 폴더를 공유 실행하지 않는다. 같은 branch를 양 OS에서 동시에 미커밋 편집하지 않고 commit/push/pull로 교환한다. 실제 hardware 권한/udev는 실물 연결 단계에서 별도 확인한다.

[Ubuntu Desktop 24.04 공식 설치 지침](https://ubuntu.com/desktop/docs/en/24.04/tutorial/install-ubuntu-desktop/)의 백업·Windows 병행/BitLocker 부분을 적용한다. 이번 문서는 실제 파티션 조작 명령을 제공하거나 실행하지 않는다.

### 2.3 소프트웨어 기준 제안

**Ubuntu24.04 LTS + ROS 2 Jazzy + Gazebo Harmonic + Nav2**를 이 프로젝트의 기본 제안으로 둔다. 현재 최신 LTS 조합이 Ubuntu26.04/Lyrical/Jetty라는 공식 안내도 확인했으나, 이번에는 문서·호환 조합이 확보된 이전 LTS를 기준으로 잡는다. 최신 버전이라는 주장이 아니며 설치일에 지원/패키지 가용성과 노트북 드라이버를 다시 확인한다.

Jazzy는 Ubuntu24.04를 지원하고 2029년5월까지 지원되는 배포판이며, Gazebo 공식 호환표는 Jazzy/Harmonic을 권장 조합으로 명시한다. [Open Robotics 릴리스 안내](https://www.openrobotics.org/blog/2024/5/ros-jazzy-jalisco-released), [Gazebo 호환표](https://gazebosim.org/docs/harmonic/ros_installation/). 기존 Humble·Classic 학습 환경은 보존하되 새 프로젝트 셸에서 배포판/overlay를 섞지 않는다. 패치 버전은 설치 후 manifest에 고정한다.

10/27 기기 조회 이력: Ryzen7 5800H, RAM약16GB, RTX3050Ti Laptop 4GB. 새 Ubuntu의 드라이버/FPS/VRAM 성능은 미측정이다. 가벼운 월드·단일 로봇·2D scan으로 시작한다. Isaac Sim 공식 요구사항(열람11/17, 페이지갱신10/14)은 최소 RAM32GB·VRAM16GB를 제시하므로 현재 노트북의 기본 경로로 잡지 않는다. Isaac Lab/새 GPU 구매가 RL 시작 조건은 아니다. ## 4. 시뮬레이션에서 먼저 고정할 계약

- 모델은 궤도형 로봇의 **차동 구동 근사**부터 시작한다. 유효 궤간·마찰·슬립·질량/관성 미확정은 파라미터 가정으로 둔다. 이상적인 바퀴 모델 결과를 실물 궤도 회전/견인 성능으로 주장하지 않는다.
- TF는 `map → odom → base_footprint → base_link`로 연결한다. 첫 지도 주행에서 AMCL이 `map → odom`을 맡고, Gazebo 차동 구동과 bridge가 `odom → base_footprint`를 연결한다. `robot_state_publisher`가 차체와 센서의 고정 변환을 발행한다. EKF를 적용할 때는 `odom → base_footprint`의 발행 주체를 EKF 하나로 바꾼다. [TF 발행 주체](../../05_ROS2_Integration/README.md#좌표계와-발행-주체)
- 센서: sensor_msgs/Imu의 m/s²·rad/s·축/중력 처리, LaserScan의 m·rad, Odometry의 m·m/s·rad/s, covariance와 timestamp를 명시한다. IMU만으로 장시간 위치가 유지된다고 가정하지 않는다.
- 센서 추정 odom과 Gazebo ground truth를 구분한다. ground truth는 평가에만 쓰고 AMCL/EKF/RL 관측에 몰래 넣어 결과를 높이지 않는다. 이상적 odom으로 먼저 동작을 확인한 경우 그렇게 표시한다.
- 전체 sim 노드는 use_sim_time/clock을 맞춘다. reset 시각 역행·센서 stale/유실, QoS·발행률/지연을 기록한다.
- 명령은 m/s·rad/s의 cmd_vel 계열이다. 실제 메시지형(Twist/TwistStamped)과 토픽명은 **설치한 Jazzy/Nav2 버전**에서 확인해 고정한다. 현재 PWM 명령에 속도를 그대로 대입하지 않는다.
- 전류·전압·온도는 별도 mock/replay provider로 먼저 노출한다. 단위(A/V/°C), source=SIM/REPLAY/REAL, valid, age, timestamp를 포함한다. 모의 온도/전류로 실제 배터리 소비·모터 발열·고장 임계값을 검증했다고 하지 않는다.
- 현재 패키지는 `tmr_description`과 `tmr_sim`이다. `tmr_bringup`, `tmr_navigation`, `tmr_monitoring`, `tmr_interfaces`는 후속 계획이며 RL은 별도 환경에서 진행한다.
- 경로는 ROS package share/상대경로로 찾고 C:\\Users 또는 D: 아카이브에 의존하지 않도록 한다. bag/동영상은 별도 artifact와 manifest로 관리한다.

Nav2 공식 가이드는 물리 로봇 없이 simulator로 TF·URDF·odometry·센서를 구성하는 순서를 제공한다. [First-Time Robot Setup](https://docs.nav2.org/rolling/configuration_and_development/first_time_robot_setup_guide/), [robot_localization](https://docs.nav2.org/rolling/configuration_and_development/first_time_robot_setup_guide/odom/setup_robot_localization/). rolling 문서의 최신 파라미터를 Jazzy에 그대로 복사하지 않는다.

## 6. 평가 기준과 RL 범위

### Nav2 첫 기준선 제안

고정된5경로×4조건/seed로20회, 동일한 모델·지도·속도 제한에서 목표 성공 수, 충돌 수, 완료 시간, 경로 길이, 최종 위치/방향 오차, 취소/통신 유실 후 요청 정지와 시뮬레이션 real-time factor를 CSV로 남긴다. 평가 지도/seed와 튜닝용을 분리한다.

초기 gate 제안은 **성공18/20 이상·평가 중 충돌0·최종 오차0.20m/10° 이내**, 취소/입력 stale 처리 재현이다. 이 수치는 제조사 보증이 아닌 작은 시뮬레이션 과제의 시작 기준이다. 속도 상한/목표 허용치·시험 환경을 먼저 고정한 뒤 판정하며 기준을 결과에 맞춰 소급 변경하지 않는다. 실물 정지 거리/안전 기준은 별도다.

### 강화학습은 무엇을 비교하는가

첫 주제는 **2D 목표 도달·장애물 회피**다. 전류/열까지 정확한 모터 모델이나 end-to-end 영상 자율주행을 첫 과제로 넣지 않는다. 관측은 제한된 scan·목표 상대 거리/각도·속도, 행동은 제한된 선속도/각속도, 보상은 목표 접근/도달·충돌·시간/불필요 회전 항으로 설계한다. 처음부터 임의 숫자를 확정하지 않고 범위/스케일·보상 악용 사례를 검사한다.

Gymnasium+Stable-Baselines3 PPO의 작은 MLP/CPU를 시작 후보로 둔다. seed별 차이와 별도 test 환경 평가를 유지한다. 학습 예산/시간·메모리는 짧은 pilot으로 정한다. [SB3 공식 RL 지침](https://stable-baselines3.readthedocs.io/en/master/guide/rl_tips.html).

규칙 제어와 RL은 같은 가벼운 환경에서 먼저 비교한다. Nav2와 우열을 비교하려면 같은 Gazebo 조건·센서 정보·속도 제한·성공 기준으로 다시 평가한다. Nav2가 전역 지도를 알고 RL은 scan만 받는 등 정보가 다른 결과는 그 차이를 명시한다. 향상 없으면 Nav2 유지·RL 결과/한계를 남기는 것도 유효한 결과다. sim-to-real 전이·노면 슬립/지연·센서오차 랜덤화는 이 기준선 이후다.

## 7. PCB와 실물 통합의 다음 상세화

전기 검토는 남은 보호 저항/퓨즈 선택, 접속부/절연, 외부 포트·전원 전이, 정상 환산비/오차 예산을 **결정표 중심으로 닫는다**. 보호 저항 TCR는 오차 기여 상한1회 계산으로 충분한지 판단하고 의미가 작으면 종료한다. 별도 온도 실습·잡음 실습을 자동 추가하지 않는다.

11/30 ELEC-01 뒤에는 결과에 따라 다음3작업을 순차 배정한다: (1) 승인된 변경만 회로/ERC·기본 PDF 반영, (2) footprint/기구·커넥터/시험점 배치 및 routing/DRC, (3) 제작 전 검토·발주 판단. 각각 독립 완료 기준을 만들며 모호한 전원/보호 조건을 날짜 때문에 임의 확정하지 않는다. 제작/배송 기간은 미정이므로 실물 주행 완료일은 잡지 않는다.

실물 자율주행 연결 gate:
1. 실제 IMU 통신·축/단위/시각·정지 drift, encoder 속도/거리·회전/슬립 특성 확보.
2. 실제 LiDAR 선정·전원/인터페이스/scan frame·설치 검토 및 데이터 수신.
3. cmd_vel의 물리 속도를 추종할 저수준 제어/속도 검증. 기존 개방루프 PWM 매퍼만으로 Nav2 추종 성능을 보장하지 않음.
4. PC→ESP32 단일 production ingress→STM32 경로, owner/기한/timeout/명령유실·재연결·물리 정지 검증. ROS나RL이 STM32의 최종 출력 권한을 우회하지 않음.
5. 남아 있는 MVP/T005A/T007 수용 경계와 인가 조건을 명시한 뒤 사용자가 감독하 저속 시험 수행. sim PASS로 기존 미결을 자동 종료하지 않음.
