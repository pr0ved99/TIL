## 확인과 근거

- [입력 안내](../plans/2026-10-12_WiFi_ARM_CMD_Executor_Code_Guide_ko.md)의 C 두 블록은 [10/12 후보 snapshot](../../assets/logs/wifi_link/2026-10-12_executor_candidate/README.md)과 줄바꿈 정규화 후 동일하다. 헤더 88줄, C 295줄이다.
- 현재 contract/ticket/owner/state 8개 파일 및 executor 검사 runner/fixture 2개 파일은 해당 snapshot과 byte가 같다. 후보의 기존 17 PASS를 인용하며 변경 없는 검사를 다시 실행하지 않았다.
- 입력 재개 당시 CMake는 기존 다섯 source만 등록했다. main은 W5 PING/DISARM 경로이며 새 제어 모듈 호출이 없다. 후보 PASS·빌드 등록은 보드 ARM/CMD 실행 증거가 아니다.
- 입력 안내에 완료 범위를 추가했다. 이번 zero-only 단계에서 계획한 신규 펌웨어 모듈은 executor 한 쌍으로 한정한다. main 연결 기능을 별도 파일로 계속 나누는 작업을 선행 조건으로 추가하지 않는다.
- 사용자 펌웨어와 CMake 수정, ESP/STM 빌드·플래시, 보드 동작, Git commit/push는 수행하지 않았다.

## executor 포함 ESP 빌드 성공 — 사용자 확인

- 사용자가 ‘빌드 성공이야’라고 보고했다. executor 포함 ESP 전체 빌드 성공으로 기록한다. 원본 빌드 로그/바이너리 식별값·새 플래시·보드 실행 결과는 별도로 보고되지 않았다.
- 현재 모듈 10개 파일과 CMake가 PC17 PASS 당시 snapshot과 byte가 같음을 확인했다. 변경 없는 PC 검사는 반복 실행하지 않았다.
- main에는 executor 참조가 아직 없다. 모듈 준비·빌드 완료와 실제 브라우저/UART ARM/CMD 연결을 구분한다. 다음은 기존 main/브라우저 연결이다.

## main 연결 전 기존 PING 흐름 확인

- 실제 main의 `ws_receive → s_wifi_command_queue → wifi_command_step → UART → wifi_command_handle_response → wifi_command_finish → s_wifi_command_result_queue → ws_command_results` 경로를 읽었다. HTTP 요청 처리는 UART 응답을 기다리지 않으며, 요청/결과를 큐에 값으로 복사한다.
- executor 연결 지점은 명령 접수, UART 송신 준비/완료, ACK/ERR·TEL·시간 감시·연결 종료다. 기존 PING 진단과 지속적인 ARM/CMD 제어의 책임 차이를 먼저 설명한다.
- 기존 W5 송신은 `s_stm_lock`을 잡은 채 `uart_write_bytes`를 호출한다. 후속 통합에서는 공유 자료 검사와 실제 송신을 분리하고, 잠금 해제 이후 취소와 이미 송신에 들어간 프레임의 처리 범위를 검증해야 한다.
- 이번 확인은 소스 흐름 분석과 설명 범위다. main 연결 코드·브라우저 변경·새 통합 검사는 아직 작성하거나 실행하지 않았다. 신규 펌웨어 파일은 추가하지 않았다.

## main·브라우저 연결 후보 준비 — C42·JS27 PASS

- 후속 ‘진행해보자’에 따라 [기존 main 전체 교체본](../plans/2026-10-13_WiFi_ARM_CMD_Main_Integration_Code_Guide_ko.md)을 작성했다. 별도 펌웨어 모듈 추가 없이 HTTP 접수·ticket·공통 seq·UART 송신/응답/TEL·기한·연결 종료와 내장 브라우저를 연결했다.
- HTTP/UART의 executor 호출은 기존 mutex로 직렬화하고 UART/네트워크 I/O는 잠금 밖으로 이동했다. UART 쓰기는 기존 UART 태스크만 수행한다. 송신 확정 뒤 취소는 해당 프레임을 회수하지 못하며 후속 DISARM으로 진행하는 경계를 기록했다.
- 수동 ARM→zero CMD100ms 목표, 새 연결 HELLO(비명령), 포커스/숨김/끊김 취소를 구현했다. DISARM은 일반 대기/간격 제한보다 우선하며 **ACK+새 TEL의 비무장·속도/PWM0 확인 뒤 OK**로 바뀐다. 정지 확인 실패는 STOP_UNCONFIRMED다.
- 후보의 선택 C 함수+실제 저장 모듈 PC 실행 **42 PASS(W5 21+연결 21)**, 내장 PAGE 모의 실행 **27 PASS**. [출력·manifest](../../assets/logs/wifi_link/2026-10-13_main_candidate/README.md)에 검사 대상/해시와 경계를 보존했다. 실제 RTOS 동시성·무선/UART·출력/정지 증거가 아니다.
- 실제 main SHA256은 W5 기준 `dfe9a97e77453378a4f5a0cc64b3dfa642244c93ec6d6259cb4742bba8d5d2b4`로 변경 없다. 사용자 모듈·CMake·개인 Wi-Fi 설정도 수정하지 않았다. ESP/STM 빌드·플래시·Git commit/push는 수행하지 않았다.
- 다음은 사용자의 전체 블록 저장 → 실제 저장본 검사 → 사용자 ESP 빌드다. AC-B/S 보드 시험은 이후 현재 전원/sense 조건을 확인하고 진행한다.

## main 저장본 검토·통합 ESP 빌드 성공

- 사용자가 ‘빌드 성공’이라고 보고했다. 실제 main 2054줄을 다시 읽어 전체 교체 안내와 줄바꿈/끝 공백 정규화 후 동일함을 확인했다. 실제 byte SHA256은 `39ab34b9f7c0b8ee3c7a10c3e638bb29fa455fed657a25d2e682ac7d1436714e`다. 기존 모듈10개 파일과 CMake는 후보 검사 때와 byte가 같다.
- 후보 안내가 아닌 **실제 저장 main**을 대상으로 C42(W5 21+연결 21)·PAGE JS27 검사를 실행해 모두 PASS했다. [출력·소스/검사 snapshot manifest](../../assets/logs/wifi_link/2026-10-13_main_review/manifest.json)를 보존했다. PC mock 검사이며 실제 RTOS 경합·무선/UART 증거가 아니다.
- main 통합 ESP 전체 빌드 성공은 사용자 확인이다. 빌드 원본 로그/바이너리 식별값·새 플래시·보드 동작은 아직 보고되지 않았다.
- 플래시 후 비구동 시험 전제 확인에 사용자가 **LiPo와 모터 드라이버 전원 모두 분리**라고 답했다. 이전 STM/ESP USB 공급·XL4015 분리 보고와 함께 유지하며 PC7 sense 상태는 추정하지 않는다.
- 다음 행동은 전원 조건 유지 후 사용자 ESP32 Flash→Monitor, 부팅/STARTUP/TEL 확인이다. ARM 조작·AC-B/S PASS를 선행 기록하지 않는다. 펌웨어 직접 수정·보드 빌드/플래시·Git commit/push는 하지 않았다.

## STM·ESP 펌웨어 교과서 제작

- 사용자가 기초부터 현재 구현까지 단계적으로 이해할 수 있는 하나의 교과서와 예제를 요청했다. 외부 `Embedded/STM32`·`Embedded/ESP32-S3`의 보드별 자료와 프로젝트 학습 노트를 확인하고, 통합 소스와의 관계를 유지하기 위해 [교과서 폴더](../../07_Embedded_Learning_Notes/06_STM32_ESP32_Firmware_Textbook/README.md)를 프로젝트 내부에 만들었다. 외부 두 학습 색인과 프로젝트 학습/문서 색인에 연결했다.
- [본문](../../07_Embedded_Learning_Notes/06_STM32_ESP32_Firmware_Textbook/STM32_ESP32_Firmware_Textbook_ko.md)은 0~20장과 부록으로 구성한다. C·빌드·GPIO·시간·ISR·UART·parser → STM 상태/출력/엔코더 → ESP 태스크/네트워크 → ticket/owner/state/executor·브라우저 취소 → 디버깅·종합 과제 순서이며, 장별 예제·문제·해설과 실제 함수 지도를 포함한다.
- 실제 저장 main은 이전 문서의 “main 미연결” 단계 이후 구현이다. 분석 시 ESP main SHA256은 `877205e6616a06ae79510e26f39f8e2b0731a928708779b83f00d66ac696afdc`다. 위의 플래시 전 기록은 당시 이력으로 유지하며 교재는 그 이후의 실제 저장 소스를 기준으로 한다.
- PC 학습 예제 C 4개를 TCC로 컴파일/실행하고 JS 1개를 Node로 실행해 모두 성공했다. parser/ring·mapper/encoder·제어 모듈은 실제 소스를 링크했다. 합성 clock/ACK/TEL과 축소 브라우저 모델이며 보드·실제 PAGE 전체 검증이 아니다. [검증 기록](../../07_Embedded_Learning_Notes/06_STM32_ESP32_Firmware_Textbook/validation.md)과 [기준 소스 해시](../../07_Embedded_Learning_Notes/06_STM32_ESP32_Firmware_Textbook/source_manifest.json)를 저장했다.
- 교재는 최근 사용자 관측의 ARM/zero·수동 정지·포커스 상실 정지·자동 재개 없음과 ticket/버튼 수정 사례를 설명하지만, AC-S 전체나 ACTIVE 중 WS close를 PASS로 올리지 않는다.
- 이번 교재 제작에서 펌웨어 수정·보드 빌드/플래시·전원 조작·Git commit/push는 수행하지 않았다. 다음 학습 시작점은 본문 0~2장과 PC 예제 01이며, 남은 실물 시험은 별도 흐름으로 유지한다.

- 펌웨어와 예제 C/JS는 변경하지 않았다. 새 보드 시험·Git commit/push는 수행하지 않았다. 이번 보완의 미해결 항목은 없으며, 다음 학습은 단위 1에서 시작해 예제 01 하나를 실행하는 것이다.

## 후속 사용자 관측과 Git 반영 준비

- 대화의 사용자 로그·화면·확인 답변을 기준으로, 통합 ESP 빌드/플래시/모니터 이후 READY·TEL 수신, DISARM seq 대응/OK, 잘못된 ticket/boot 거부, 두 창의 요청자별 결과, 재접속 뒤 자동 송신 없음 관측을 정리했다. 이는 대화 기반 관측 요약이며 연속 보드 원본 로그를 새로 수집했다는 뜻이 아니다.
- zero-only ARM 이후 화면의 ACTIVE·STM ARMED/NONE·PWM/CPS0, 수동 DISARM 버튼 조작, VS Code로 전환할 때 IDLE로 돌아감과 정상 동작을 사용자가 확인했다. ticket 만료 진단 뒤 브라우저 여유/수동 준비 대기 보완과 IDLE ARM 버튼 깜빡임 해소도 확인했다. ACTIVE 중 WS 단절·전체 AC-B/S·nonzero 주행 수용으로 확대하지 않는다.
- 초기 LiPo/모터 전원 분리 이후 사용자는 PC7 동작에 LiPo가 필요하다고 설명하고 '#1만 분리'를 보고했다. ESTOP_LATCHED 뒤 STM reset 후 DISARMED/BOOT 로그를 제공했다. 종료 전원 상태와 최신 플래시 바이너리 hash는 미확인이다.
- Git 반영 전 실제 main SHA256 `877205e6616a06ae79510e26f39f8e2b0731a928708779b83f00d66ac696afdc`의 C42·PAGE JS46을 실행해 모두 PASS했다. [현재 출력·manifest](../../assets/logs/wifi_link/2026-10-13_git_closeout/manifest.json)에 보존했다. 검사 대상은 선택 C 함수/모듈과 모의 브라우저이며 보드 빌드나 실제 무선 검증은 아니다.
- 사용자 요청에 따라 state/executor·main 연결·검사·단계별 근거·교과서·예제·관련 목차를 커밋/푸시 대상으로 정리했다. snapshot의 SHA256이 줄바꿈 변환으로 깨지지 않도록 해당 근거 폴더의 `.gitattributes`를 지정했다. 기존 Hello World tracked build 변경과 개인 Wi-Fi header는 포함하지 않는다.
