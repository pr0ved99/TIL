오늘 실행 결과의 근거는 사용자가 제공한 진행 기록과 대화 보고다. 이번 정리에서 새 원본 모니터 로그·캡처·실행 바이너리 해시는 확인하지 않았다. 사용자 완료 보고를 유지하며 문서 확인을 새 보드 시험으로 기록하지 않는다. 여러 화면에 같은 메시지를 전달하는 기능을 학습했으며 여러 장치의 동시 조종 권한을 확정한 것은 아니다.

앞선 03 학습의 TAG·콜백·DHCP·RSSI·핸드셰이크와 Flash/NVS 설명은 복습 기준으로 유지한다. 오늘은 로컬 SDK의 `wifi_config_t` 정의(`esp_wifi_types_generic.h` 608행)를 열어 AP/STA/NAN 설정 공용체와 현재 `sta` 사용을 확인했다. C/C++ 확장 설치·포맷 설정을 확인하고 주석 색상 변경 방법을 안내했다. 설정 적용 완료로 기록하지 않는다.

## 실제 코드와 대조한 내용

- STM [`uart_mvp_protocol.c`](../../03_Firmware/stm32_uart_mvp/Core/Src/uart_mvp_protocol.c)의 `TEL_PERIOD_MS=100u`: TEL 전송을 약 100ms 간격으로 시도한다. 모든 UART 패킷의 공통 송수신 주기가 아니다.
- STM [`main.c`](../../03_Firmware/stm32_uart_mvp/Core/Src/main.c)의 `ENCODER_SPEED_SAMPLE_PERIOD_MS=100U`: 엔코더 속도 계산 기준 주기다. 타이머의 펄스 계수와 구분하며 현재 1ms PID 제어 완료를 뜻하지 않는다.
- 기존 ESP bench는 CMD 재전송 100ms·TEL age 감시 250ms·CMD timeout 500ms다. 250ms는 ESP의 TEL 감시 값이며 STM의 공통 정지 timeout이 아니다. STM 기본 CMD timeout은 300ms, 허용 범위는 50~500ms다.
- 실제 TEL은 `t_ms/state/reason/command_age_ms/last_seq/vx_mmps/w_mradps/left_pwm/right_pwm/left_cps/right_cps/batt_mv/drop/err` 형식이다. `batt_mv=0`은 고정 자리표시자다. 배터리 전압·잔량 실측으로 표시하지 않으며 RPM·누적 tick은 별도 기존 TEL 항목이 아니다.
- 현재 프로토콜은 줄바꿈으로 끝나는 ASCII 프레임이다. 프레임·필드·범위·sequence 검증을 CRC/체크섬 구현 완료라고 표현하지 않는다.
- [`esp32_wifi_link`](../../03_Firmware/esp32_wifi_link/main/wifi_link_main.c)는 현재 HTTP 폴링·ESP 자체 상태 표시다. 05 예제의 성공이 실제 앱의 WebSocket 또는 W4 완료는 아니다.

## 모의 데이터와 실시간성 설명 정리

사용자는 지금 점퍼선이 없으며 집에서 STM/ESP UART를 연결해 실제 W4를 진행할 계획이라고 밝혔다. ESP 내부 Dummy Task와 100ms 모의 TEL 생성은 다른 대화의 제안이며 구현·빌드·실행 완료 보고는 없다. 현재 다음 행동은 실제 UART 연동 준비다.

모의 데이터는 화면·직렬화·파서 입력 실험에 사용할 수 있으나 UART 배선·실제 프레임 수신·수신 중단을 검증하지 못한다. 사용할 경우 `MOCK` 출처를 명시하며, 실제 수신 함수 한 줄로 모든 통합이 끝난다고 가정하지 않는다.

WebSocket/TCP/Wi-Fi는 일정 시간 내 도착·화면 갱신의 보장 수단이 아니다. 대화의 고정 최소 지연, 20~50Hz 보편적 한계, 100ms 표준, 현재 STM의 1ms PID·0.1ms 전력 차단 설명은 실제 근거와 구분해 정정했다. 자세한 설명·계산·출처는 [타이밍과 W4 데이터 흐름 노트](../../07_Embedded_Learning_Notes/01_Concept_Notes/10_ESP32_WiFi_WebSocket_Timing_and_W4_Dataflow_ko.md)를 따른다.

## 미완료와 집에서 이어갈 순서

1. 실제 앱의 WebSocket 상태 전송 및 UART 수신·snapshot·stale 표시 구현을 사용자 입력 방식으로 진행한다. 저장 파일 검토 뒤 사용자가 빌드·플래시한다.
2. 집에서 GPIO17/18↔STM PA10/PA9 및 공통 GND, 현재 앱·전원 조건을 확인하고 기존 UART 계약의 실제 TEL을 받는다. 기존 완료한 도통·모터 시험을 반복하는 단계가 아니다.
3. 실제 TEL과 브라우저 표시를 대조한 뒤 UART 수신 중단·재접속을 확인한다. W4는 상태 전달이며 ARM/CMD·모터 구동은 W5의 별도 범위다.

배터리 ADC·RPM 표시 확장, W5 무선 명령, 로봇 전류·발열·주행과 PCB 제작은 이번 결과에 포함하지 않는다. 이번 문서 정리에서는 펌웨어 수정·빌드·플래시·배선 작업을 수행하지 않았다.
