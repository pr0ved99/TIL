# NAV-03 반복 평가 조건과 예비 주행

[로드맵](../../../../docs/plans/2026-11-17_Ubuntu_Nav2_Simulation_and_RL_Roadmap_ko.md#6-평가-기준과-rl-범위) · [11/23 진행 기록](../../../../docs/progress/2026-11-23_progress.md)

평가용 방 B의 시드 4101~4104 결과는 별도 기록에 있다. 이 문서의 시드 3101~3104는 예비 주행 조건이다. [정식 평가 결과](../2026-11-23_tmr_nav03_evaluation/README.md)

## 시험 입력

매 회차 Gazebo, 지도 서버, AMCL, Nav2를 새로 시작한다. Gazebo 월드와 AMCL의 초기값은 모두 `(x, y, yaw) = (0, 0, 0)`이다. 원점에서 정지한 상태로 시뮬레이션 시계, `map → base_footprint`, `/scan` 360개 표본과 정면 약 1 m를 확인하고, `/bt_navigator`가 `active`가 된 뒤 목표를 보낸다. 목표의 좌표계는 `map`, 단위는 m와 rad이다. Gazebo 월드 자세는 주행 결과를 측정할 때 사용한다.

| 경로 | 목표 x, y (m) | 목표 방향 | 조사할 동작 |
| --- | --- | ---: | --- |
| P01 | (0.60, 0.00) | 0° | 직진 |
| P02 | (0.20, 0.85) | +90° | 좌회전 후 전진 |
| P03 | (0.20, −0.85) | −90° | 우회전 후 전진 |
| P04 | (−0.85, 0.60) | 180° | 뒤쪽 목표로 이동 후 방향 정렬 |
| P05 | (1.50, 0.55) | 0° | 방 안쪽 고정 벽 우회 |

[routes.yaml](routes.yaml)의 5경로를 Gazebo 시드 3101, 3102, 3103, 3104와 조합해 총 20회로 계획한다. 이 시드 값은 `gz sim --seed`에 전달하며, AMCL과 MPPI 내부의 난수·실행 타이밍까지 동일하다고 가정하지 않는다. 목표 취소, 주행 중 새 장애물, 센서 입력 중단은 각 동작을 확인하는 별도 회차로 기록한다.

월드는 [11/22 방과 기존 안쪽 벽, 고정 지도](../2026-11-22_tmr_lidar_amcl/README.md)를 사용한다. 기존 벽은 월드 (1.115, 0, 0.20) m에 둔다. NAV-02에서 추가한 대각선 벽은 이 시험 월드에 생성하지 않는다. Jazzy Nav2 1.3.14, Gazebo Harmonic 8.15.0, TMR의 0.270 × 0.268 m 직사각형 외곽, 0.05 m 비용 지도 셀, 0.70 m 인플레이션, 전후진 ±0.10 m/s 및 각속도 ±0.39 rad/s를 사용했다. [입력 파일 SHA-256](inputs.sha256)

현재 Nav2의 도착 판정은 위치 0.25 m와 방향 0.25 rad다. 로드맵의 초기 성능 기준안은 위치 0.20 m와 방향 10°다. 평가 CSV에서 액션 결과와 Gazebo 기준 위치·방향 오차를 각각 기록한다. 시간, 경로 길이, 최종 정지, 복구 횟수, 실시간 계수와 충돌 관측도 각 회차에 남긴다. 아래 예비 주행은 도착 판정과 정지를 확인하는 데 사용했고 충돌 계측을 포함한 정식 20회에는 합산하지 않았다.

## 같은 조건으로 실행

ROS 2와 빌드된 TMR 워크스페이스를 로드한 Bash를 사용한다. 각 터미널에서 `ROS_DOMAIN_ID=86`, `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST`, `GZ_PARTITION=tmr-nav03-pilot`를 동일하게 설정한다. TMR 프로젝트 루트에서 방과 지도 파일 경로를 준비한다. 다른 seed를 시험할 때는 아래 값을 바꾸고 세 프로세스를 모두 새로 시작한다.

```bash
export ROS_DOMAIN_ID=86 ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST
export GZ_PARTITION=tmr-nav03-pilot
export TMR_NAV_ROOM="$PWD/assets/logs/ros2/2026-11-22_tmr_lidar_amcl"
```

1. 첫 터미널에서 `ros2 launch tmr_sim drive.launch.py headless:=true seed:=3101`을 실행한다. 창 없이 GPU LiDAR 렌더링이 동작하는 구성을 사용한다.
2. 두 번째 터미널에서 아래 두 모델을 차례로 생성한다.

   ```bash
   ros2 run ros_gz_sim create -world empty -name tmr_nav_test_room -file "$TMR_NAV_ROOM/room.sdf"
   ros2 run ros_gz_sim create -world empty -name scan_test_wall -file "$TMR_NAV_ROOM/scan_test_wall.sdf" -x 1.115 -y 0 -z 0.2
   ```

3. 세 번째 터미널에서 `ros2 launch nav2_bringup localization_launch.py use_sim_time:=true autostart:=True use_composition:=False map:="$TMR_NAV_ROOM/room.yaml"`를 실행한다. `map_server`와 `amcl`이 활성화된 뒤 아래 서비스 요청으로 시작 자세를 입력한다.

   ```bash
   ros2 service call /set_initial_pose nav2_msgs/srv/SetInitialPose \
     '{pose: {header: {frame_id: map}, pose: {pose: {orientation: {w: 1.0}}}}}'
   ```

4. 네 번째 터미널에서 `ros2 launch tmr_sim navigation.launch.py`를 실행한다. `ros2 lifecycle get /bt_navigator`가 `active [3]`을 반환하고 자세와 스캔을 확인한 뒤, 명령 터미널에서 P01 목표를 보낸다.

   ```bash
   ros2 action send_goal /navigate_to_pose nav2_msgs/action/NavigateToPose \
     '{pose: {header: {frame_id: map}, pose: {position: {x: 0.60, y: 0.0}, orientation: {w: 1.0}}}}'
   ```

## 위치 허용치 0.15 m 비교

같은 경로 P01, 시작 자세, Gazebo 시드 3101·3102를 사용해 새 월드에서 두 회차를 추가 실행했다. 도메인 86의 `/controller_server`에서 활성 플러그인 `general_goal_checker.xy_goal_tolerance`를 실행 중 0.25 m에서 0.15 m로 바꿨다. 목표를 보내기 전에 위치 0.15 m와 방향 0.25 rad를 각각 읽어 확인했다. 0.15 m는 로드맵의 위치 오차 기준안 0.20 m보다 5 cm 안쪽인 비교용 설정이다.

```bash
ROS_DOMAIN_ID=86 ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST ros2 param set \
  /controller_server general_goal_checker.xy_goal_tolerance 0.15
```

| Gazebo 시드 | 0.25 m 설정의 위치 오차 | 0.15 m 설정의 위치 오차 | 0.15 m에서 도착까지 |
| --- | ---: | ---: | ---: |
| 3101 | 24.10 cm | 13.73 cm | 4.80초 |
| 3102 | 24.33 cm | 13.68 cm | 4.85초 |

위치 오차는 정지 후 Gazebo 월드에서 측정했다. 0.15 m 회차는 두 번 모두 `SUCCEEDED`, 복구 0회였고 마지막 `/cmd_vel` 및 이후 약 2초간 `/odom` 60개 표본의 속도 여섯 성분이 모두 0이었다. 이 결과는 P01 직진에 해당한다. 회전이 포함된 경로의 최종 방향 오차와 충돌은 정식 평가에서 관측한다. [3101 비교 표본](tolerance-0p15-3101.json) · [3102 비교 표본](tolerance-0p15-3102.json) · [활성 YAML 항목](../../../../05_ROS2_Integration/src/tmr_sim/config/nav2_params.yaml#L92)

## 회전 경로의 방향 허용치 비교

위치 허용치를 0.15 m로 고정하고 방향 허용치 0.25 rad(14.3°)와 0.12 rad(6.9°)를 비교했다. 평가 기준안 10° 안쪽에 여유를 둔 후보로 0.12 rad를 선택했다. P02는 목표 (0.20, 0.85) m와 방향 +90°, 시드 3101을 사용했다. P03은 (0.20, −0.85) m와 방향 −90°, 시드 3102를 사용했다. 네 회차에서 새 월드를 각각 열었다. 액션이 벽시계 45초까지 끝나지 않으면 시험 코드가 목표를 취소했다. 두 허용치 적용 범위는 도메인 86의 실행 중인 컨트롤러였다. [Nav2 SimpleGoalChecker](https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/core_servers/controller_server/controller_server_plugins/simple_goal_checker/)

| --- | ---: | --- | ---: | ---: | ---: |

취소 세 회차는 `Failed to make progress`와 복구 4회를 기록했다. 도착한 P02는 복구 0회였다. 네 회차 모두 마지막 속도 명령과 정지 후 약 2초간 연속 오도메트리 60개 표본의 속도 여섯 성분이 0이었다. 종료 시 방향 오차는 네 회차 모두 10° 이내였고, 취소한 세 회차는 지도 위치 오차가 설정한 15 cm 밖이었다. 회전 경로의 다음 비교에서는 목표 근처 위치 오차와 진행 확인기의 이동량을 함께 기록한다. 현재 `SimpleProgressChecker`는 10초 안에 위치가 0.50 m 바뀌었는지 본다. [Nav2 SimpleProgressChecker](https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/core_servers/controller_server/controller_server_plugins/simple_progress_checker/)

## P03 진행 확인기의 최소 이동량 비교

새 월드 세 회 모두 시드 3102, 시작 (0, 0, 0°), 목표 (0.20, −0.85, −90°), 도착 위치·방향 허용치 0.15 m·0.12 rad, 진행 확인 시간 10초를 사용했다. 도메인 86의 실행 중 `progress_checker.required_movement_radius`만 0.50 m와 0.10 m로 비교했다. 45초가 지나면 시험 코드가 액션을 취소했다. Gazebo 시드는 같고 AMCL·MPPI의 내부 타이밍과 난수는 각 회 달라질 수 있다.

| 최소 이동량 | 액션 결과 | 첫 진행 부족 판정 | 복구 | 정지 후 Gazebo 위치 오차 |
| --- | --- | ---: | ---: | ---: |
| 0.50 m | 45초 경과 후 시험 취소 | 18.07초 | 4 | 21.17 cm |
| 0.10 m | 12.05초에 도착 | 발생 없음 | 0 | 21.60 cm |
| 0.10 m 반복 | 45초 경과 후 시험 취소 | 23.97초 | 4 | 21.34 cm |

세 회 모두 정지 후 Gazebo x가 약 −0.01 m였다. 목표 x는 +0.20 m이며, 정지 방향은 모두 −90°에서 4.2° 이내였다. 취소 두 회는 35~44초 구간에서 지도 기준 x 변화가 0.1 mm 미만이었다. 목표 방향인 −90°를 맞춘 자세에서 주로 남은 위치 오차는 +X 방향이었다. 각 회차의 마지막 `/cmd_vel`과 이후 약 2초의 오도메트리 60표본은 여섯 성분 전부 0이었다.

10 cm 첫 회차가 `SUCCEEDED`를 반환할 무렵 액션 피드백에서 샘플링한 최소 지도 거리는 약 15.04 cm였고 정지 후 TF로 읽은 거리는 15.87 cm였다. 진행 중 표본과 정지 후 위치는 시점이 다르다. 세 회의 Gazebo 오차는 모두 20 cm 평가 기준안을 넘었다. 같은 시드의 두 번의 10 cm 시험에서 도착 여부가 달라졌으므로, 이 결과만으로 10 cm를 정식 평가 설정으로 고정하기 어렵다.

목표 부근에서 전역 경로가 +X로 이어졌고, 제어기가 선택한 궤적에서는 이 방향의 이동이 거의 없었다. 속도는 평활기와 충돌 모니터에 들어가기 전부터 작았다. 정지 시 지도에서 추정한 x가 Gazebo x보다 4.84 cm 컸다. 두 좌표계의 원점과 축은 시험 시작 때 맞췄다. 위치·경로·속도는 서로 다른 주기로 수신했으며 16초 비교에는 가장 가까운 표본을 썼다. 속도 메시지별 발행자 GID는 제공되지 않아 주행 명령 비교를 첫 복구 전 구간으로 한정했다. `/transformed_global_plan`과 `/optimal_trajectory`는 `controller_server` 단독 발행이었다.

다음 비교 후보는 `FollowPath.GoalAngleCritic.threshold_to_consider`이다. 현재 값은 0.50 m이며 목표 방향 오차를 궤적 비용에 반영하기 시작하는 거리다. 0.15 m와 한 변수만 바꾸어 비교하면 목표 옆에서 자세를 일찍 맞추는 경향에 이 항목이 기여하는지 시험할 수 있다. 이번 관측은 원인이나 최적값을 확정하지 않는다. ## P03 목표 방향 비용 적용 거리 비교

P03 목표 (+0.20 m, −0.85 m, −90°)에서 `FollowPath.GoalAngleCritic.threshold_to_consider`를 0.50 m와 0.15 m로 비교했다. 시드 3102는 0.50 → 0.15 m, 시드 3103은 0.15 → 0.50 m 순으로 새 월드를 시작했다. 같은 시드 안에서는 적용 거리 한 항목만 다르다. 도메인 86 전용 YAML 사본을 시작할 때 전달하고 초기화 로그와 실행 중 파라미터 조회로 적용 거리를 검증했다. 각 회차 공통 조건은 위치 허용치 0.15 m, 방향 허용치 0.12 rad, 진행 확인기 0.50 m·10초, 방향 비용 가중치 3.0이다.

## P02 좌회전 목표 방향 비용 적용 거리 비교

## P01 직진과 물리 접촉 계측

P01 직진에서 같은 후보(방향 비용 적용 거리 0.15 m, 위치 허용치 0.15 m, 방향 허용치 0.12 rad)로 두 번 모두 복구 없이 도착했다. 시드 3102·3103의 Gazebo 위치 오차는 13.82·14.06 cm, 방향 오차는 0.97·1.21°였다. 센서로 관측한 장애물 접촉은 두 회차 모두 0회였고, 시험 뒤 약 2초 동안 정지를 확인했다. 별도 월드에서 차체를 고정 벽에 두 번 닿게 하여 2,435개 장애물 접촉 레코드가 2회로 집계되는 것을 확인했다. 바닥 접촉은 별도 집계했다.

다음은 후보 설정과 정식 평가에 쓸 지도·시드를 확정하고 5경로 × 4조건의 20회 평가를 수행하는 것이다. 앞선 예비 주행은 정식 횟수에서 제외한다. [P01 결과·교정 절차·원자료](p01_contacts/README.md)
